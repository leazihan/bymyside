# 周复盘与周规划

周日复盘后生成下周安排；未完成则周一兜底。同一周只交付一次，普通修订更新 week-plan.md。启用周推送前须获得用户授权，系统先拟时间安排草案，用户补变化；不代做用户业务任务。

## 复盘只做有依据的检查

根据已有进展核对已完成结果、剩余量、估算偏差和现实变化。实际耗时未知就不生成注意力占比。不强制遍历九维、记录模式或每周改变策略。
区分估算错误、信息缺失、约束变化、优先级取舍与执行阻碍，不直接归因为能力。发现有可复用证据时才保留候选模式或提出实验。

## 拟定周安排

读取 life-map 的阶段方向和长期投入，再读取 projects.md 的近期责任、具体期限、剩余量及到期复核想法。结合日程表和生活安排计算可用窗口。
检查最晚启动时间与剩余工作量，主动安排长期重要项和无开始日期但时机合适的想法；不要只看最近截止。

输出：
- 本周各项目预期结果及其阶段里程碑关联。
- 每日拟推进结果、适合的窗口与大致工作量；不提前锁死所有具体钟点。
- 已保护的生活时间、缓冲、延期风险与需要决定的取舍。
- 暂缓项原因和复核日期；有明确未来窗口则写窗口。

安排覆盖明确请求，估算总量应与可用量相容。不相容时展示缺口和方案；信息不足时标草案和假设，不能承诺完成。
收尾按 memory-protocol.md 执行：同步当前对象、完成事项出列、待复核项检查；具备 Python 3 与文件维护权限时运行归档预览，复核 needs_review 并标记已吸收的旧记录，再运行归档工具；不具备时跳过自动归档、保留原文并记录维护待处理，不影响规划。记录实际结果一行即可，不能只写“归档完成”而未执行。周一兜底包含同一收尾，不另写全量执行报告。

## 评估系统是否有用

使用已有资料每周检查：遗漏请求、时间冲突/估算偏差、日周阶段关联、重复询问/过期提醒、用户反馈时间与纠正次数。未知数据标未知，任务完成率仅辅助。
查看重复读取/写入、记录量和运行延迟；只在已有日志支持时报告成本，不编造 token 或时长。
约十五分钟为初始用户参与预算。连续使用两周后据实际问题改流程，不因单次事故新增永久规则。
